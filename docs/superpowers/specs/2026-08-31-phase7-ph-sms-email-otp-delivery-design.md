# Phase 7 Philippine SMS and Email OTP Delivery Design

## Goal

Make Sprint 9 Phase 7 deployment-ready by delivering real one-time verification codes through the correct production channels: Resend for customer email OTP and Semaphore for Philippine mobile SMS OTP, while preserving the existing customer-auth security model, anti-enumeration behavior, OTP lifecycle, session handling, and OWNER/STAFF separation.

## Scope

This design applies to `m1/v0.9/feat/customer-mobile-otp`.

Included:

- Register new email -> real email OTP through Resend.
- Login existing verified email -> real email OTP through Resend.
- Register new Philippine mobile -> real SMS OTP through Semaphore.
- Login existing verified Philippine mobile -> real SMS OTP through Semaphore.
- Existing OTP hashing, expiry, single-use behavior, failed-attempt handling, resend controls, rate limiting, remembered-account behavior, and generic anti-enumeration responses.
- Server-side provider configuration and sanitized delivery failures.
- Automated provider-boundary tests plus live manual QA readiness.

Not included:

- Non-Philippine mobile numbers.
- WhatsApp, Viber, Telegram, voice-call OTP, or international SMS.
- Replacing Resend for email delivery.
- Changing Google/social authentication.
- Changing OWNER/STAFF authentication.
- Exposing OTP values, provider API keys, or account-existence state to the browser.

## Current Root Cause

Email OTP is already implemented with Resend. Registration intentionally returns a generic success without sending when the email already belongs to an existing customer, preserving anti-enumeration behavior. Login email OTP requires an active eligible customer email and uses the same generic public request response.

Mobile OTP currently has no real SMS provider. In development, the backend logs the generated code to the terminal and returns success; in test it performs no delivery; outside development/test it throws a delivery-unavailable error. This means the current mobile flow is not deployment-ready even though challenge generation and verification are implemented.

## Architecture

The backend remains authoritative for OTP generation and verification. YsabelleStore generates the six-digit OTP, hashes it before persistence, enforces the existing ten-minute lifetime, applies single-use and failed-attempt rules, and creates the customer session only after successful verification.

A new focused Semaphore delivery service will own only outbound SMS transport. It will receive the already-generated normalized Philippine mobile number and verification code, send it through Semaphore's dedicated OTP endpoint, and return success or a sanitized delivery error. The provider never becomes the source of truth for OTP verification.

Email remains on the existing Resend delivery service. The two channels remain independent so SMS-provider failures cannot affect email delivery and Resend failures cannot affect mobile verification.

## Philippine Mobile Contract

Only Philippine mobile numbers are accepted.

Accepted user formats remain:

- `09XXXXXXXXX`
- `639XXXXXXXXX`
- `+639XXXXXXXXX`

The backend continues to normalize these to canonical `+639XXXXXXXXX` form. Any non-PH number is rejected before delivery.

For Semaphore transport, the delivery adapter converts the canonical number to the provider-compatible Philippine form without weakening application-level validation.

## Semaphore Provider Contract

Use Semaphore's dedicated OTP API endpoint:

`POST https://api.semaphore.co/api/v4/otp`

Required request values:

- `apikey`: server-only API key.
- `number`: normalized Philippine destination.
- `message`: Ysabelle Store OTP copy containing `{otp}`.
- `code`: the six-digit OTP generated by YsabelleStore.
- `sendername`: configured approved sender name when present.

Semaphore's OTP route is specifically for OTP traffic and supports supplying a caller-generated code. YsabelleStore therefore keeps its existing OTP lifecycle rather than accepting a provider-generated secret.

The application must treat non-2xx responses, malformed responses, or provider statuses indicating failure as delivery failure. Provider response bodies must never be surfaced directly to customers.

## Environment and Secret Contract

Add backend-only environment variables:

```env
SEMAPHORE_API_KEY=
SEMAPHORE_SENDER_NAME=YSABELLE
```

Rules:

- Never commit a real API key.
- Never expose these values through `VITE_*`, browser bundles, Electron renderer code, logs, API responses, or error messages.
- `SEMAPHORE_API_KEY` is required for real mobile delivery outside test.
- `SEMAPHORE_SENDER_NAME` is optional at code level so Semaphore can use the account default sender name, but production deployment should configure the approved Ysabelle sender.
- Development must use the real provider when credentials are configured; it must not silently fall back to logging the OTP.
- Test environments use injected fake delivery functions and never call Semaphore over the network.

## SMS Copy

Keep the message concise and within one SMS segment where possible:

`Ysabelle Store code: {otp}. Expires in 10 minutes. Do not share this code.`

No account name, email address, internal id, or other private customer data is included.

## Email Delivery Contract

Continue using the existing Resend integration for both registration and authentication emails.

Registration email rules:

- A new eligible email receives a six-digit verification code.
- An email already attached to an existing customer receives no registration OTP.
- The public response remains generic so account existence is not disclosed.

Login email rules:

- An active eligible verified customer email receives a six-digit sign-in code.
- Missing, inactive, or ineligible accounts receive the same generic public request response.
- Provider delivery errors are logged only as sanitized events and must not disclose whether the account exists.

## Mobile Registration Rules

- A new valid PH mobile number can receive a real SMS OTP.
- A mobile number already attached to an existing customer receives no registration OTP and still gets the generic public response.
- The verification challenge is deleted/invalidated if provider delivery fails so an undelivered code cannot remain valid.
- Successful verification creates the existing registration verification grant; no session is created until registration completes.

## Mobile Login Rules

- Only an active customer with the exact verified PH mobile number is eligible for an SMS sign-in code.
- Ineligible numbers receive the same generic public response.
- Successful verification creates the existing customer session and preserves remembered-account behavior.
- Delivery failure invalidates the just-created challenge and is surfaced internally as a sanitized delivery failure without revealing account existence.

## Anti-Enumeration and Error Handling

Public request endpoints keep generic success responses regardless of whether the email/mobile belongs to an eligible customer. This prevents using OTP endpoints to enumerate registered customers.

The system may record sanitized events such as:

- `customer_email_registration_delivery_failed`
- `customer_email_auth_delivery_failed`
- `customer_mobile_registration_delivery_failed`
- `customer_mobile_auth_delivery_failed`

Logs must not contain:

- OTP code
- Semaphore API key
- full provider response body
- raw session token
- password/reset secret

The mobile service may log a masked phone suffix or internal event metadata when needed, but never the OTP.

## Resend and Cooldown Behavior

Preserve existing ten-minute OTP expiry and 30-second resend cooldown behavior where already implemented. Repeated requests inside the cooldown must not create or send a new OTP.

Mobile registration must receive equivalent resend/cooldown protection if the current implementation lacks it, so repeated button presses cannot generate uncontrolled SMS cost.

## Provider Failure Semantics

Provider transport failure must not leave a usable undelivered challenge.

For both registration and login mobile flows:

1. Generate and persist the challenge.
2. Attempt Semaphore delivery.
3. If delivery succeeds, keep the challenge active.
4. If delivery fails, delete or consume that challenge before returning to the controller.
5. Controller preserves anti-enumeration semantics and logs only the sanitized failure event.

Configuration failure is a provider delivery failure, not a reason to print OTP values in development.

## Testing Strategy

Automated tests must use dependency injection/fakes and no real network calls.

Required coverage:

- PH normalization accepts the three supported input forms and rejects non-PH numbers.
- Semaphore adapter sends the configured endpoint, server key, destination, caller-generated code, message template, and optional sender name.
- OTP values and API keys are absent from logs and public responses.
- Provider success leaves the challenge usable.
- Provider failure removes the newly created challenge.
- Mobile registration new number sends once and can verify successfully.
- Mobile registration existing number sends nothing and preserves generic public response.
- Mobile login verified active number sends once and creates a session only after correct verification.
- Mobile login unknown/unverified/inactive number sends nothing and preserves generic public response.
- 30-second resend cooldown prevents duplicate provider sends.
- Expired, replayed, and incorrect codes fail.
- Existing failed-attempt limits remain enforced.
- Email registration new email invokes Resend delivery.
- Email registration existing email performs no delivery but preserves generic response.
- Email login eligible email invokes Resend delivery.
- Email login ineligible email performs no delivery but preserves generic response.
- Existing customer-auth frontend, backend, social auth, recovery, remembered-account, and internal-auth-boundary tests remain green.

## Manual Live QA

After provider credentials are configured, QA must test with real controlled identities:

1. Register with a brand-new email and confirm the Resend OTP arrives.
2. Register with a brand-new PH mobile number and confirm the Semaphore SMS OTP arrives.
3. Complete registration and confirm both verified identities are stored as expected.
4. Logout and sign in through Email Quick Sign using the registered email.
5. Logout and sign in through Mobile Quick Sign using the registered PH number.
6. Test resend cooldown, wrong code, expired code, and one-time use.
7. Confirm existing registration email/mobile values do not receive registration OTP and do not reveal that the account exists.
8. Confirm login with unknown email/mobile gives the same public request response.
9. Confirm customer session/logout behavior and remembered-account behavior remain correct.

## Deployment Requirements

Before production deployment:

- Create and fund a Semaphore account.
- Configure `SEMAPHORE_API_KEY` in the deployment secret store.
- Register/approve the intended Semaphore sender name and configure `SEMAPHORE_SENDER_NAME`.
- Configure the existing Resend production sender/domain and `RESEND_API_KEY`/`CUSTOMER_RECOVERY_FROM_EMAIL` secrets.
- Perform live QA on at least one Globe/Globe-family and one Smart/Smart-family controlled test number when practical.
- Verify provider balance/availability monitoring and operational ownership.

## Acceptance Criteria

Phase 7 delivery readiness is achieved only when:

- Register Email uses real Resend delivery for eligible new emails.
- Login Email uses real Resend delivery for eligible existing customer emails.
- Register Mobile uses real Semaphore SMS delivery for eligible new Philippine mobile numbers.
- Login Mobile uses real Semaphore SMS delivery for eligible verified Philippine mobile numbers.
- No development path prints usable OTP values as a substitute for SMS delivery.
- Anti-enumeration behavior remains intact.
- OTP generation, hashing, expiry, single-use rules, failed attempts, rate limits, and session boundaries remain intact.
- Provider failures cannot leave usable undelivered challenges.
- Targeted and full Tier 3 auth/security verification is green except for clearly unrelated pre-existing repository failures.
- Live provider QA can be completed using deployment secrets without code changes.

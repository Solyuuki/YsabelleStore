# Sprint 5 Definition of Done

Sprint 5 has two completion layers:

- **Repository-side implementation** — code, guidance, persistent context, freshness, routing, MCP/Skill configuration, tests, and deterministic benchmark tooling.
- **External coding-agent validation** — live Codex/compatible-host loading and actual model usage metrics that cannot be generated by the repository itself.

Repository-side work is complete when the requirements below are implemented and regression-tested. Final empirical host validation remains a separate evidence step when a compatible host is available.

## Knowledge and Guidance

- [x] Existing major project guidance has been audited/classified.
- [x] Current project scope has a canonical source.
- [x] Current repository layout and module ownership have canonical sources.
- [x] Known stale folder/status/scope contradictions no longer drive normal context routing.
- [x] Golden Rules are a compact cross-cutting policy/router rather than a domain knowledge dump.
- [x] Stable architecture/business knowledge is separated from change-sensitive implementation evidence.
- [x] The context layer is explicitly a cache/navigation layer, not a competing source of truth.

## Persistent Context

- [x] A compact repository index exists and can be regenerated deterministically.
- [x] The index records repository commit/branch and dirty-path freshness state.
- [x] Changed paths can be detected without a model-driven full-repository scan.
- [x] Mapped changes can refresh affected context incrementally.
- [x] Unmapped/unsafe changes can fall back to a full refresh.
- [x] Context can be reused by separate sessions that use the same checkout.
- [x] Retrieval auto-builds only when persistent context is missing.

## Agent Behavior

- [x] The project Skill starts from persistent task context instead of broad exploration.
- [x] Routine context retrieval performs freshness handling automatically.
- [x] Primary implementation files are distinguished from secondary dependencies.
- [x] Broad discovery is an evidence-based escalation rather than the default.
- [x] Normal reversible implementation continues without unnecessary permission prompts.
- [x] Acceptance criteria and risk-based verification remain required before completion.
- [x] Unrelated refactoring is explicitly discouraged.

## Verification

- [x] Local, subsystem, and full verification tiers are documented.
- [x] Intermediate iteration uses the least expensive sufficient verification tier.
- [x] Expensive passing checks are not rerun without a relevant reason.
- [x] Full verification remains the requirement for high-risk/release-sensitive changes.
- [x] Context mismatches can be recorded and refreshed.
- [x] Repository-context regression tests cover freshness, persistence, file priority, and routing behavior.
- [x] Repository-context regression tests are included in `verify:code`.

## Benchmark

- [x] A deterministic context-footprint/routing benchmark exists.
- [x] The benchmark explicitly states that its token estimate is a proxy, not model billing.
- [x] Representative storefront, POS/inventory, and auth/database pilot routing is documented.
- [x] Proxy/pilot acceptance criteria include file budget, escalation, freshness, and verification tier.
- [ ] Actual model token/iteration/retry metrics are recorded from a compatible coding-agent host.
- [ ] Live Codex Skill + project MCP loading is demonstrated in a fresh host session.

The final two items are external empirical validation, not missing repository implementation.

## Safety Rule

If token-saving behavior conflicts with correctness, approved project requirements, inventory/data integrity, security, or required validation, correctness and project requirements take priority.

## Closure Rule

Do not claim live Codex performance improvements from repository proxy data alone. Once a compatible host is available, add live evidence to `PILOT-BENCHMARKS.md` and only tune the repository again if that evidence identifies a real problem.
